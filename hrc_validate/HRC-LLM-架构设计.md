# HRC-LLM：分层循环压缩语言模型 v0.17

> **Hierarchical Recurrent Compression LLM**
> 一种面向超长上下文的非对称编码—记忆—解码架构
>
> **v0.17 核心：极长上下文（N→4M）下 GPS 会 O(n²) 爆炸——改用采样 + cross-attention 变 O(1)；补数值稳定性四件套；新增「检索即记忆写入」能力**
> **保留 v0.5 约束：选择只在 ENCODE 阶段，DECODE 零选择**
>
> 基于五轮深度调研 + 实算验证修订。文末「设计红线」列出所有被证据推翻的设计选择。

## 摘要

HRC-LLM 采用非对称三段式结构：**重编码器**做自适应压缩，**记忆桥**做分级保真，**轻解码器**做恒定成本生成。

$$
\underbrace{\text{编码器}}_{\text{重, }46.6\%}\;\longrightarrow\;\underbrace{\text{记忆桥}}_{\text{轻, }2.6\%\text{ 但决定成败}}\;\longrightarrow\;\underbrace{\text{解码器}}_{\text{中, }50.7\%}
$$

**v0.17：一个"只在标准长度下成立"的设计缺陷**

**① GPS 在 N>1M 时会 O(n²) 爆炸**

全局预打分（GPS）用块摘要做全连接注意力。我一直是按 N=131,072 算的：

| N | 摘要数 | self-attention | 判定 |
|---:|---:|---:|---|
| 131,072 | 2,048 | 6.44 G | OK |
| 1,048,576 | 16,384 | 412 G | ⚠️ |
| **4,194,304** | **65,536** | **6,597 G** | ❌ **比整个 encode 还贵 35x** |

> **我一开始想用"分层 GPS"救，但那是错的**——分层只减了 L2，L1 仍是 O(n²)。

**正确方案：采样 + cross-attention**

| 方案 | N=4M 成本 | 性质 |
|---|---:|---|
| self-attention（当前） | 6,597 G | O(n²) |
| 两级 cross-attention | 414 G | 仍 O(n) |
| **采样 4096 + cross-attn** | **3.22 G** | **O(1)，与 N 无关** |

**GPS 只做粗打分，后续有 stage-1/2 精修**——所以采样漏掉部分摘要是可接受的。

**② 数值稳定性：4 个此前完全没讨论的风险**

| 风险 | 缓解 |
|---|---|
| 记忆桥循环更新（梯度跨步） | 遗忘门 bias +1 **但可训练**；每 512 步截断 BPTT |
| 三级精度（1.0/0.25/0.0625）梯度尺度不一 | 每档存储前 RMSNorm |
| **MoE + 级联双重离散** | **STE + 负载均衡 + 熵正则**（最大训练风险） |
| 位置外推 | RoPE（块内）+ 可学习（块间）；训练混合长度 |

**③ 新能力：检索即记忆写入**

记忆桥是固定大小 KV 集合，**外部检索结果可直接写入，且可持久化**：

| 场景 | 标准 RAG | **HRC** | 加速 |
|---|---:|---:|---:|
| 10 文档 × 10 查询 | 1,235 ms | 14.8 ms | **83x** |
| 100 文档 × 100 查询 | 115,472 ms | 148 ms | **780x** |
| 1,000 文档 × 1,000 查询 | 11,466,832 ms | 1,481 ms | **7,742x** |

> 标准 RAG 每次查询都要 re-prefill 全部文档。**HRC 编码一次，记忆持久化复用。**

## 零之零零零零零零零零零零零、v0.17：极长上下文与稳定性

### 00000000000.1 GPS 在 N>1M 时会爆炸

全局预打分（GPS）用块摘要做**全连接注意力**。我此前全部按 N=131,072 计算：

| N | 摘要数 | self-attention | 判定 |
|---:|---:|---:|---|
| 131,072 | 2,048 | 6.44 G | ✅ |
| 1,048,576 | 16,384 | 412 G | ⚠️ |
| **4,194,304** | **65,536** | **6,597 G** | ❌ **比整个 encode（190 G）还贵 35x** |

**一个我先提出又自我否决的方案**：分层 GPS（每 8 个摘要聚合成 1 个）。

$$\text{L1} = 65536^2 \cdot d \cdot 2 \quad \text{—— 分层只减了 L2，L1 仍然是 } O(n^2)$$

**这个方案是错的。**

### 00000000000.2 ★ 正确方案：采样 + cross-attention

| 方案 | N=4M 成本 | 性质 |
|---|---:|---|
| self-attention（当前） | 6,597 G | $O(n^2)$ |
| 两级 cross-attention | 414 G | 仍 $O(n)$ |
| **采样 4096 + cross-attn** | **3.22 G** | **$O(1)$，与 N 无关** |

**关键实现**：GPS 不用 self-attention，改用 **M=256 个可学习 latent query 去 cross-attend** 采样出的 4096 个摘要：

$$\text{cost} = M \cdot 4096 \cdot d \cdot 2 \cdot 2 = \text{常数}$$

| N | 采样 | 成本 |
|---:|---:|---:|
| 1,048,576 | 4,096 / 16,384 | **3.22 G** |
| 4,194,304 | 4,096 / 65,536 | **3.22 G** |

> **可行性依据**：GPS 只做**粗打分**，后续有 stage-1（30%）和 stage-2（10%）精修。
> 采样漏掉的部分摘要，其信息仍可通过块摘要进入后续流程。
>
> ⚠️ **必须验证**：采样对 stage-1 召回的影响。若 recall@128 下降 >1%，需增大采样数。

### 00000000000.3 数值稳定性：4 个此前完全没讨论的风险

| # | 风险 | 描述 | 缓解 |
|---|---|---|---|
| 1 | **记忆桥循环更新** | 每 512 token 写入，梯度跨步累积 | 遗忘门 bias **+1 但可训练**（Block-Recurrent 原文）；每 512 步截断 BPTT；更新量 clamp |
| 2 | **三级精度** | 1.0 / 0.25 / 0.0625 梯度尺度不一致 | 每档存储前 RMSNorm；梯度 scale 补偿 |
| 3 | **MoE + 级联双重离散** | 路由与选择都是离散决策，梯度极稀疏 | **STE 直通估计 + 负载均衡 loss + 熵正则** |
| 4 | **位置外推** | 训练 8K 推 131K+ | RoPE（块内）+ 可学习（块间）；训练时混合长度 |

> **风险 3 是本架构最大的训练风险。** MoE 路由已经是一层离散决策，级联选择是第二层。
> 两者叠加会导致**梯度极度稀疏**——这是 v0.16 打分器退化问题的放大版。

### 00000000000.4 ★ 新能力：检索即记忆写入

**记忆桥是固定大小的 KV 集合——外部检索结果可以直接写入，且可持久化。**

| | 标准 RAG | **HRC 记忆写入** |
|---|---|---|
| 首次编码 | O(N) prefill | O(N) 编码进记忆 |
| 后续查询 | **O(N) 重 prefill** | **O(1) 读记忆** |
| 增量文档 | 全部重算 | **增量写入** |
| 跨会话 | 不可复用 | **记忆持久化** |

| 场景 | 标准 RAG | **HRC** | 加速 |
|---|---:|---:|---:|
| 10 文档 × 10 查询 | 1,235 ms | 14.8 ms | **83x** |
| 100 文档 × 100 查询 | 115,472 ms | 148 ms | **780x** |
| 1,000 文档 × 1,000 查询 | 11,466,832 ms | 1,481 ms | **7,742x** |

> 加速比随 Q 线性增长，因为**标准的 re-prefill 成本是每查询全额支付，HRC 只付一次**。

**这把 HRC 从"长上下文模型"变成了"可持久化的记忆系统"**——标准 KV cache 是位置绑定的临时产物，HRC 的记忆是可累积的资产。

>

## 零之零零零零零零零零零零、v0.16：训练侧补盲

### 0000000000.1 前 15 个版本的一个系统性盲区

v0.1 到 v0.15，我优化的全部是**推理**。编码、解码、记忆、带宽、并发——没有一处在谈训练。

v0.16 第一次系统审视训练，**立刻发现一个可能让整个架构失效的问题**。

### 0000000000.2 ★ 级联选择的梯度困境

推理时 stage-2 只处理 **10%**（T1）的段。训练时呢？

**如果只给被选中的 10% 回传梯度**：

```
打分器 → 选中 top-10% → stage-2 → loss → 梯度回传
                     ↑
              只有这 10% 有梯度
              漏掉的 90% 从未被惩罚
```

**结果**：打分器只看得到"我选中了什么"，**看不到"我漏掉了什么"**。没有负样本信号 → **打分器退化**，无法学会区分 10% 与 90% 的边界。

> 这是稀疏/路由架构的经典问题：MoE 的 load balancing loss、NSA 的可微门控，都是在解决这个问题。
> **我在设计中完全没有对应的机制。**

**四种方案对比**

| 方案 | 训练算力 | 打分器质量 | 风险 |
|---|---:|---|---|
| 仅选中段（naive） | 1.0x | **低** | 打分器退化 |
| 直通估计 STE | 1.3x | 中 | 梯度有偏 |
| 辅助 oracle 打分器 | 1.5x | 高 | 需 oracle 标签 |
| **全量 stage-2** | **5.52x** | 最高 | 训练贵 5.5x |

### 0000000000.3 ★ 预算课程学习（推荐方案）

**核心思想：训练时宽预算，推理时紧预算，逐步收紧。**

$$\rho_{train}: 50\% \to 30\% \to 20\% \to \rho_{infer}=10\%$$

| 阶段 | T1 | encode | vs 推理成本 |
|---|---:|---:|---:|
| 初期 | 50% | 480.7 G | 2.98x |
| 中期 | 30% | 335.8 G | 2.08x |
| 后期 | 20% | 263.4 G | 1.63x |
| **推理** | **10%** | 190.9 G | 1.18x |

**三个好处**：

1. **平均训练成本 ~1.5–2x**，而非全量的 5.5x
2. **宽预算期打分器见过更多正样本** → 收紧后判断更准
3. **天然的稳定性**：先学"什么重要"，再学"只留最重要的"

**必须与 v0.6 登记的反事实标签机制配合**：用 $\Delta_b = \ell(Y|\mathcal{H}_{-b}) - \ell(Y|\mathcal{H}_{-b}\cup\{x_b\})$ 作为 oracle 监督信号。

### 0000000000.4 首次量化：MoE 的显存代价

前面只算了 MoE 的**算力收益**（8 选 1/2），没算**显存代价**：

| | 参数 | 显存 | 每 token 激活 |
|---|---:|---:|---:|
| stage-0 MoE 8 专家 (d=256) | 6.3 M | 12.6 MB | — |
| stage-1/2 MoE 8 专家 (d=512) | 25.7 M | 51.4 MB | — |
| **MoE 合计** | **32.0 M** | **64.0 MB** | 14.4 MB |
| 稠密等效 | 7.2 M | **14.4 MB** | 14.4 MB |

> **MoE 用 4.4x 的显存换取算力节省。**
> 在长上下文场景（显存本就紧张，v0.12 指出并发受限于此），**这可能是亏的**。

**另一个 MoE 特性**：batch=1 时只读激活的 14 MB，但 **batch≥8 时 8 个专家可能都被访问**，要读全部 64 MB。

> 这解释了 v0.7 那个反直觉结论：MoE 在小 batch 有效、大 batch 失效。

**待消融**：MoE vs 稠密+更窄，在 80 GB 显存约束下的实际吞吐。

### 0000000000.5 训练算力（顺带确认）

| | 每 token 训练 |
|---|---:|
| HRC | **7.40 MFLOPs** |
| 同规模稠密（6N 法则） | ~516 MFLOPs |
| **比值** | **省 70x** |

> 训练算力**不是瓶颈**。真正的训练问题是**梯度质量**（0000000000.2），不是算力。

### 0000000000.6 训练侧的完整方案

```
阶段 1（宽预算 T1=50%）
  ├─ 全局预打分通道训练
  ├─ 打分器用 oracle Δ_b 监督
  └─ 重建损失（attention-reconstruction，非 CE）

阶段 2（收紧 50%→30%→20%）
  ├─ 每档验证 stage-1 召回 ≥98%、final ≥95%
  └─ 未达标则回退上一档并延长训练

阶段 3（推理 T1=10%）
  └─ 冻结打分器，只微调解码器
```

**关键闸门**：每一档收紧前必须验证召回，不达标就停在这一档。

> 这直接对应 v0.9 登记的推翻条件："若 d=256 在 oracle 选择器下也无法达到目标召回，继续压缩没有意义。"

## 零之零零零零零零零零零、v0.15：解码瓶颈的物理切换

### 000000000.1 修正：又一处口径不自洽

解码器权重从 v0.7 起就按 **GQA g=8** 算（$2d^2 + 2d^2/8$，其中 $2d^2/8$ 是 K/V 投影）。

**但 KV cache 我一直按 MHA 全维度算**（$W \cdot d \cdot 2 \cdot 2 \cdot L$）——两套口径打架了。

| | 错误（MHA 口径） | **正确（GQA g=8）** |
|---|---:|---:|
| 每 token 每层 KV | 2,560 B | **320 B** |
| 窗口 KV (W=512, 8 层) | 10.49 MB | **1.31 MB** |
| **解码总 KV** | **12.45 MB** | **3.28 MB** |

### 000000000.2 ★ 由此发现：瓶颈发生了 regime change

| | 权重 | KV | 主导 |
|---|---:|---:|---|
| 全注意力基线 | 134 MB（5%） | **2,416 MB（95%）** | **KV-bound** |
| **HRC v0.15** | **29.9 MB（90%）** | 3.28 MB（10%） | **weight-bound** |

> **O(1) 记忆把 KV 打掉了 99.9%，瓶颈就从 KV 转移到了权重。**
>
> 这是个好消息，也是个警告：**好消息**是 KV 已不是问题；**警告**是我前面几轮还在优化 KV（三级路由省 44%），那 44% 只占总解码的 6%。

**正确的优先级**：权重（90%）>> KV（10%）。

## 零之零零零零零零零零、v0.14：三级记忆金字塔

### 00000000.1 问题：二值决策的代价

v0.13 把预算从 5% 提到 15%，做法是**把 15% 的段全部存成满精度**。副作用：

$$\text{stage-2 处理量}: 5\% \to 15\% \quad\Rightarrow\quad \text{encode}: 140\ G \to 183\ G\ (+32\%)$$

这暴露了更根本的问题：**我一直在做二值决策（留 / 不留），但压缩精度是连续量。**

### 00000000.2 三级金字塔

| 档 | 覆盖 | 精度 | 编码深度 | 存储 |
|---|---:|---:|---|---:|
| **T1 精确原文** | 10% | 1.0 | stage-2 深层 | 40.3 MB |
| **T2 中精度** | 20% | 0.25 | stage-1 中层 | 20.1 MB |
| **T3 低精度** | 50% | 0.0625 | stage-0 浅层 | 12.6 MB |
| **合计** | **80%** | — | — | **73.0 MB** |

**核心结构：存储精度 ↔ 编码深度对齐**

```
stage-0 (100% token, d=256) ──→ T3 (50%, 1/16 精度)   便宜覆盖
        ↓ 25%
stage-1 (T1+T2, d=512)     ──→ T2 (20%, 1/4 精度)    中等保真
        ↓ 10%
stage-2 (T1, d=512)        ──→ T1 (10%, 满精度)      精确保真
```

> **浅层只配低精度，深层才配高精度。** 这是本轮最重要的结构性洞察——它同时省了编码算力和存储。

### 00000000.3 配置扫描

| T1 | T2 | T3 | 记忆 | vs MHA | encode | 精确 tok | 覆盖 |
|---:|---:|---:|---:|---:|---:|---:|---:|

| **10%** | **20%** | **50%** | **73.0 MB** | **33x** | **161.6 G** | **13.1K** | **80%** |
| 15% | 20% | 50% | 93.1 MB | 26x | 197.8 G | 19.7K | 85% |
| 15% | 30% | 60% | 105.7 MB | 23x | 227.2 G | 19.7K | 105% |

**推荐 T1=10%**：精确证据 13.1K token（v0.12 的 2x），覆盖 80%，encode 比 v0.13 省 12%。

### 00000000.4 解码：三级 coarse-to-fine 路由

80% 覆盖意味着 key 数量巨大（平铺需要 17,203 keys = 211 MB/token，不可行）。

**分层路由**：

| 级 | 内容 | 字节 |
|---|---|---:|
| 粗筛 | T3 全部 2,048 段 @ d=48 | **0.39 MB** |
| 精读 | top-128 从 T1/T2 @ d=640 | 1.57 MB |

### 00000000.5 ⚠️ 最大风险：粗筛召回

**T3 只有 d=48，能可靠地把查询路由到正确的 T1 段吗？**

若粗筛漏掉，T1 里的精确信息**也取不出来**——整个金字塔失效。

| 风险 | 缓解 |
|---|---|
| 粗筛漏选 | **过度召回**（top-5% 而非 top-1%），精读层再排序 |
| 低精度语义漂移 | T3 用**独立训练的路由表示**，不是 T1 的简单降维 |
| 验证指标 | **粗筛 recall@128 ≥ 99%** |

> 这个指标不过关，金字塔就是负收益——不如 v0.13 的"15% 统一满精度"。

### 00000000.6 一个我算错又修正的模型

最初我用 KKT 求最优精度分配：

$$p_i = \frac{1}{\kappa}\ln\frac{s_i \kappa}{\lambda}$$

解出来 **"0 个满精度段"**。这个荒谬结果说明模型错了：

> $f(p) = 1-e^{-\kappa p}$ 假设**语义压缩收益连续**。
> 但**精确检索是阶跃的**——0.58 精度存不住 "7423"。

**必须有两类价值函数并存**：

| 类型 | 价值函数 | 最优策略 |
|---|---|---|
| 语义 / gist | 连续、凹 | 广铺低精度 |
| 精确 / 数值 | **阶跃** | 少量满精度 |

→ 这正是三级金字塔的理论依据，**不是拍脑袋的三档**。

## 零之零零零零零零零、v0.13：预算机制重构

### 0000000.1 一个被埋藏 9 个版本的设定错误

**5% 精确证据预算是我在 v0.4 拍脑袋定的**，理由是"全局精确预算固定 5%"。此后 9 个版本全部沿用，从未质疑。

精确重算记忆桥：

| 组件 | 计算 | 字节 |
|---|---|---:|
| L0.5 精确证据 | 960 keys × 768 × 2(KV) × 2B | 2.95 MB |
| L1 波记忆 | 64 slot × 768 × 2B | 0.10 MB |
| L2 粒子槽 | 256 slot × 768 × 2(KV) × 2B | 0.79 MB |
| L3 循环状态 | 16 × 768 × 2B | 0.02 MB |
| **合计** | | **3.86 MB** |

对照（N=131,072, d=768）：全 token 单层 KV = **403 MB**，MHA 6 层 = **2,416 MB**。

> **压缩比是 626x，不是我一直报的 89x。**
> 我之前用"27 MB"是个从没验证过的估算值。

**这意味着：即便保留 30% 的 token 作精确证据，仍比 MHA 省 20x。5% 毫无必要地激进。**

### 0000000.2 ★ 概念澄清：我一直混淆了两种"保留率"

调研给出的最关键区分：

| | 含义 | 控制什么 | 能否事后调整 |
|---|---|---|---|
| **写入预算 ρ** | 固定记忆容量（永久保留多少） | **显存** | ❌ encode 时锁定 |
| **激活预算 k** | 每步查询读取多少 | **带宽** | ✅ 查询时动态 |

**文献中那些"低保留率"数字，几乎全是激活预算**：

| 方法 | 保留率 | 实际类型 |
|---|---:|---|
| Quest (passkey) | 1% | 查询页选择，**全 KV 未删** |
| MoBA (32K, top-3) | 4.69% | 查询块选择 |
| NSA (selection) | 7.81% | 查询时激活 |
| SnapKV (1024) | 20.5% | 固定 prompt KV |

> **我把"激活预算"当成了"写入预算"来对标，这是错误的类比。**
> Quest 保留 1% 仍能精确，是因为**全量 KV 还完整躺在显存里**，只是不读。
> HRC 的 L0.5 是**永久压缩**——删掉的 95% 再也回不来了。

### 0000000.3 默认预算：5% → 15%

| 写入 ρ | 精确 token | L0.5 keys | 固定记忆 | vs MHA | 压缩 |
|---:|---:|---:|---:|---:|---:|
| 5%（旧） | 6.6K | 205 | 21.0 MB | 115x | 20x |
| 10% | 13.1K | 410 | 41.2 MB | 59x | 10x |
| **15%（新默认）** | **19.7K** | **614** | **61.3 MB** | **39x** | 6.7x |
| 20% | 26.2K | 819 | 81.4 MB | 30x | 5x |
| 30% | 39.3K | 1229 | 121.7 MB | 20x | 3.3x |

**15% 的依据**：
- 低成本检索任务（passkey）1%–5% 激活即可（Quest 实证）
- **复杂推理与生成需要 10%–20% 的写入保真度**
- MoBA 在 128K 上取 top-12 时保留率回升到 **37.5%**，RULER 0.7818 vs 全注意力 0.7849
- 15% 时仍比 MHA 省 39x，边际成本极低

### 0000000.4 ★ 双预算解耦（本轮最重要的结构性改进）

**写入 15% 保证召回，激活 top-512 保证带宽——两者解耦。**

写入 614 个段（19.7K token）进 L0.5，但解码时每步只 cross-attend 读其中 **top-512**：

| 激活 keys | 带宽/token | vs 旧(960) |
|---:|---:|---:|
| 128（快档） | 12.7 MB | 0.55x |
| 256 | 14.3 MB | 0.62x |
| **512（推荐）** | **17.4 MB** | **0.76x** |
| 960（旧） | 22.9 MB | 1.00x |

> 写入量决定**能不能找到**，激活量决定**每步花多少带宽**。
> 旧设计把两者绑成一个数字，导致"想要召回就得付带宽"的错误权衡。

### 0000000.5 质量旋钮：ρ 按任务动态选择

| 任务 | ρ | 记忆 | vs MHA | 依据 |
|---|---:|---:|---:|---|
| passkey / 单针检索 | 2% | 9.0 MB | 270x | Quest: 1% 激活即近乎完美 |
| 单文档 QA | 10% | 41.2 MB | 59x | 证据集中 |
| **默认 / 通用** | **15%** | 61.3 MB | 39x | 本报告推荐锚点 |
| 长文档摘要 | 25% | 101.6 MB | 24x | 需全局覆盖 |
| 多跳推理 | 20% | 81.4 MB | 30x | 需证据子图协同 |
| 代码库 / 精确复制 | 30% | 121.7 MB | 20x | 数值/标识符敏感 |

> **压缩率成为推理时可调节的超参**（类似 temperature），这是 O(1) 记忆带来的独特自由度。
> 固定 KV cache 架构做不到——它的容量由序列长度决定，不由你决定。

### 0000000.6 多文档记忆合成

| 文档数 | 等效 token | **HRC @15%** | MHA |
|---:|---:|---:|---:|
| 10 | 1.3M | 613 MB | 24.2 GB |

| 100 | 13.1M | 6,131 MB | 241.6 GB |

**80 GB 单卡 @15%：容纳 ~1,304 份 131K 文档 = 171M token。标准 MHA 只能 33 份（4.3M token）。**

⚠️ **但"可合并"≠"无冲突"**。多文档竞争有限槽位时会出现覆盖、干扰与检索冲突。必须显式设计：
1. **写入门控**（新颖度触发）
2. **淘汰策略**（LRU / 分数衰减）
3. **路由隔离**（文档 ID 作为路由特征）
4. **记忆编辑**（可删除/注入特定事实）

否则 O(1) 容量会从优势变成系统性瓶颈。

### 0000000.7 文献工作点对照（诚实版）

|---|---:|---|---|

## 零之零零零零零零、v0.12：从"更快"到"能做什么"

### 000000.1 纠错：v0.11 的自适应刷新收益被夸大

v0.11 报告"1M 单针检索 +2.18x"。**这是错的。**

我把自适应刷新率应用到了 prefill：

$$e_{wrong} = c_{ar}\cdot(N + 1.125M) \quad \text{vs} \quad e_{right} = e_{pt}\cdot N + c_{ref}\cdot 1.125M$$

**prefill 的 N 个 token 是输入，必须全部读一遍**；自适应只针对生成过程中**新增**的 token。

## 零之零零零零零、v0.11：纠错、修正与证伪

### 00000.1 纠错：v0.10 的草案方案是负收益

v0.10 我写："草案 = 解码器前 2 层 + cross-attn + 早退头，**复用 MoD shallow path，不需要新参数**"。

**这个建议是错的。**

| 草案方案 | 字节 | γ=8, α=0.75 |
|---|---:|---:|
| **自投机前 2 层 + 完整头**（v0.10 所写） | 29.1 MB | **0.84x** ❌ |
| 自投机前 2 层 + 高频头 | 18.8 MB | 1.15x |
| 独立 d=256 小草案 | 5.2 MB | 2.30x |
| **EAGLE 式（复用特征 + 小 head）** | **4.7 MB** | **2.39x** ✅ |

**原因**：解码器 d=640，**单层就有 8.4 MB**。前 2 层 = 16.8 MB，加上输出头 12.3 MB = 29.1 MB。
而独立草案用 d=256，2 层只要 3.1 MB。

> **"复用现成层不需要新参数"这个直觉，在带宽受限下是陷阱**——参数成本为零，但**每次草案前向都要重新读取这些字节**。
> 传统投机解码论文很少报告草案的 HBM 字节成本，因为它们的目标模型是数十亿参数，草案开销相对很小。**HRC 的解码器只有 45.9 MB，草案的相对成本被放大了。**

**EAGLE 实测支撑**：MT-Bench、温度 0 下首 token 接受率 **0.73–0.79**，平均接受长度 **3.62–3.98**。与我 γ=8、α=0.75 的 E[接受]=3.70 吻合。

### 00000.2 修正：周期刷新成本被漏算 10–19x

场景公式只算了 prefill，漏掉了生成过程中的周期刷新：

$$e_{old} = e_{pt} \cdot N \quad\Rightarrow\quad e_{new} = e_{pt} \cdot (N + 1.125 M)$$

| 场景 | 旧 | 新 | 低估 |
|---|---:|---:|---:|
| 长文档问答 | 140.0 G | 140.1 G | 1.00x |
| 长文档摘要 | 35.0 G | 37.4 G | 1.07x |
| 多轮长对话 | 8.75 G | 18.6 G | 2.12x |
| 长思维链 | 4.38 G | 43.8 G | **10x** |
| 书籍生成 | 8.75 G | 166.3 G | **19x** |

> 修正后，**解码仍然主导所有场景**（长思维链 324 ms vs encode 0.17 ms），所以 v0.10 的"解码是主战场"结论不变。但数字必须诚实。

### 00000.3 新增：自适应刷新（条件触发取代固定周期）

**动机**：生成的内容中，大部分是"流畅连接"，不是"关键事实"。为什么要给它们全部做深层编码？

**方案**：借鉴 **Titans 的 surprise-gated 更新**：

$$M_t = (1-\alpha_t)\,M_{t-1} + S_t,\quad \alpha_t = g(\text{surprise})$$

HRC 的对应实现：**stage-0 输出廉价新颖度分数 → 超阈值才触发 stage-1/2 深层编码**。

| 深编码率 | 刷新成本 | 省 |
|---:|---:|---:|
| 100%（固定周期） | 1.068 M/tok | — |
| 50% | 0.642 M/tok | 40% |
| **30%（推荐）** | **0.471 M/tok** | **56%** |
| 10% | 0.301 M/tok | 72% |

**设计**：把"何时刷新"从固定周期改为**预算控制问题**

$$\min\ \text{quality\_loss}(\text{refreshes}) + \lambda \cdot \text{total\_encode\_MACs}$$

**触发条件**（两级）：
1. stage-0 新颖度分数 > 阈值
2. 或累计未刷新新颖度超过预算

否则只做轻量的 slot/key 更新（L1/L2），不跑 stage-1/2。

> ⚠️ **stage-0 分数不能直接等同于 Titans 的 surprise**——后者是关联记忆损失的输入梯度。必须经过 recall、陈旧度、端到端延迟三方校准。

### 00000.4 证伪：L2 驻留的收益被严格限定

我一度设想：解码器权重 45.9 MB，H100 L2 是 50 MB，能驻留 → 带宽从 HBM 3 TB/s 升到 L2 ~7 TB/s → 近 10x。

**这个想法有多处错误。**

**错误 1：容量不是"接近"就等于"可驻留"**

| 平台 | L2 | fp16 45.9 MB | int8 22.9 MB | int4 11.5 MB |
|---|---:|---|---|---|
| A100 | 40 MB | ❌ 溢出 | ✅ | ✅ |
| H100 | 50 MB | ⚠️ **临界 91.8%** | ✅ | ✅ |
| H20 | 60 MB | ⚠️ 临界 | ✅ | ✅ |
| B200 | 126 MB | ✅ | ✅ | ✅ |

L2 还要容纳 **KV cache、激活、指令、并发内核的持久区域**。"容量接近" ≠ "带宽替代 HBM"。

**错误 2：KV cache 必须走 HBM**

每 token 的 KV（22.3 MB）是不同的，**不可能被 L2 复用**。

| 权重 L2 命中 | 权重时间 | KV 时间 | 总计 | 加速 |
|---:|---:|---:|---:|---:|
| 0% | 15.29 µs | 7.43 µs | 22.73 µs | 1.00x |
| 50% | 10.92 µs | 7.43 µs | 18.36 µs | 1.24x |
| 90% | 7.43 µs | 7.43 µs | 14.86 µs | 1.53x |
| **100%** | 6.55 µs | **7.43 µs** | 13.99 µs | **1.62x** |

> **即使 100% 权重 L2 命中，上限也只有 1.62x**，因为 KV 那 7.43 µs 是硬的。

**错误 3：L2 命中与投机解码收益部分重叠**

两者都在减少权重读取，不可简单相乘：

| | 顺序 | EAGLE 投机 | |
|---|---:|---:|---|
| 无 L2 命中 | 22.73 µs | 9.51 µs | 2.39x |
| 50% 命中 | 18.36 µs | 7.37 µs | 2.49x |
| 80% 命中 | 15.73 µs | 6.08 µs | 2.59x |

**正确做法**：不重写成本公式，而是
1. 用**逐层持久窗口**（L2 persistence）提高命中率
2. MoD 使活跃权重低于名义值 → 实际工作集更小
3. **必须用 `dram__bytes` profile 校准**，不能理论推

### 00000.5 树状投机：不采用

## 零之零零零零、v0.10：解码才是主战场

### 0000.1 交叉点：M* = 24.6 tokens

**这是我这轮最重要、也最打脸的一个数字。**

我把 encode 从 5,572 G（v0.6）一路砍到 140 G（v0.9），**省了 97.5%**。但对旗舰场景"长文档问答"（N=131,072, M=100）：

| | 耗时 | 占比 |
|---|---:|---:|
| **encode**（一次性） | **0.56 ms** | **20%** |
| **decode**（100 token × 22.7 µs） | **2.27 ms** | **80%** |

$$oxed{M^* = 0.56\text{ ms} / 22.7\ \mu\text{s} = 24.6\ \text{tokens}}$$

**只要生成超过 25 个 token，解码就主导。**

全场景验证（v0.9）：

| 场景 | N | M | encode | decode | 主导 |
|---|---:|---:|---:|---:|---|
| 长文档问答 | 131,072 | 100 | 0.56 ms | **2.3 ms** | decode |
| 代码库理解 | 262,144 | 500 | 1.12 ms | **11.4 ms** | decode |
| 长文档摘要 | 32,768 | 2,000 | 0.14 ms | **45.5 ms** | decode |
| 长思维链 | 4,096 | 32,768 | 0.02 ms | **744.9 ms** | decode |
| 书籍生成 | 8,192 | 131,072 | 0.04 ms | **2,980 ms** | decode |

> **六个场景，全部解码主导。** 唯一的例外是"1M 单针检索"（M=16 < 24.6）。
>
> 这意味着：继续攻 encode 的边际收益已经很低。**v0.10 冻结编码器。**

### 0000.2 自投机解码：把顺序读取变成批量读取

**原理**：batch=1 顺序解码时，每个 token 都要把 45.9 MB 权重从 HBM 读一遍（算术强度 0.21 FLOP/byte，100% 带宽受限）。

自投机把这件事**批量化**：
1. 草案模型（2 层 d=256，5.2 MB）连续生成 γ=8 个候选
2. 完整模型**一次前向**验证 9 个 token —— **权重只读一遍**
3. 接受的 token 全部保留，拒绝的按验证分布重采样（**分布无损**）

**字节账**：

| 项目 | 字节 |
|---|---:|
| 草案（γ=8 次 × 5.2 MB） | 41.6 MB |
| 验证权重（一次） | 45.9 MB |
| 验证 KV（一次，batch 共享） | 22.3 MB |
| **每轮合计** | **109.8 MB** |
| E[接受]（α=0.75, γ=8） | 3.70 |
| **每 token** | **29.7 MB** |

**68.2 → 29.7 MB/token（2.30x）**

### 0000.3 ★ HRC 的独特优势：草案模型也能"看见"全文

标准自投机（如 Medusa、EAGLE）的草案模型只有**近期上下文**，所以 α 通常只有 0.5–0.7。

**HRC 的草案模型可以 cross-attend 读记忆桥（960 keys，O(1)）**——它和完整模型看到的是同一份压缩记忆。

> 这是本架构一个此前未被利用的结构优势：**O(1) 记忆让"廉价草案"第一次有可能拥有全局视野。**

**实现方式**：草案 = 解码器前 2 层 + cross-attn + 早退头。
**这正是 MoD 的 shallow path —— 基础设施已经存在，不需要新参数。**

### 0000.4 ⚠️ α 是最大的不确定项，必须实测

我给了 2.30x，但这依赖 α=0.75。**这是假设，不是结论。**

| α | γ=4 | γ=6 | γ=8 | γ=12 | 判定 |
|---:|---:|---:|---:|---:|---|
| 0.50 | 1.48x | 1.36x | 1.24x | 1.04x | 草案基本无效 |
| 0.60 | 1.77x | 1.67x | 1.54x | 1.30x | 保守 |
| **0.70** | 2.13x | 2.10x | 1.99x | 1.72x | **标准自投机水平** |
| **0.80** | 2.58x | **2.71x** | 2.69x | 2.47x | **HRC 预期** |
| 0.90 | 3.14x | 3.58x | 3.81x | 3.90x | 乐观 |

**即使 α 只有 0.6（草案几乎不比标准好），也有 1.67x。**

> 必须先在真实任务上测 α。若 α<0.5，应放弃自投机，改为**增大 decode batch**（权重读取在多请求间摊销）——这是 servability 层面的解法，不是架构层面的。

**另一个诚实前提**：batch=1。若 batch=32，权重读取已被摊销 32x，此时解码回到算力受限，自投机的收益会显著下降。

### 0000.5 理论下限

| 不可压缩部分 | 字节/token |
|---|---:|
| 窗口 KV（W=512, 8 层） | 10.5 MB |
| cross KV（960 keys, 4 层） | 9.8 MB |
| **纯 KV 下限** | **22.3 MB** |

## 零之零零零、v0.9：双轨优化（编码算力 / 解码带宽）

### 000.1 轨道分离：两个瓶颈，两套打法

我一直用 MACs 衡量两侧成本。**这是错的——两侧受限类型根本不同。**

| | 算术强度 | H100 机器平衡 | 判定 | 有效手段 |
|---|---:|---:|---|---|
| **ENCODE** | **8,337 FLOP/byte** | ≈333 | **算力受限** | 降 FLOPs（级联、窄 stem、MoE） |
| **DECODE** (b=1) | **0.21 FLOP/byte** | ≈333 | **带宽受限** | **降字节**（层跳过、簇路由、量化） |

> 强度差 4 个数量级。把它们放在同一张表里比较，本身就是错误。

### 000.2 解码轨：真实的成本是字节

| N=131072 | 权重 | KV cache | 合计/token |
|---|---:|---:|---:|
| 全注意力 | 134 MB | **2,416 MB** | **2,550 MB** |
| **HRC** | 45.9 MB | **22.3 MB（O(1)）** | **68.2 MB** |

**每生成一个 token，全注意力要把 2.4 GB 的 KV cache 从 HBM 读一遍。**

→ **HRC 真正的架构优势是 KV 的 O(1)，而不是 MACs 的 14x。**

**诚实分列**（架构收益与量化收益**不可重复相乘**）：

| 口径 | 全注意力 | HRC | 比 |
|---|---:|---:|---:|
| 都未量化（**纯架构收益**） | 2,550 MB | 68.2 MB | **37.4x** |
| 都 int4 权重 + KIVI int2 KV（**对等最优**） | 336 MB | 14.3 MB | **23.5x** |
| 基线 int2 KV / HRC fp16（对基线最有利） | 436 MB | 68.2 MB | 6.4x |

> **应报告 23.5x（对等量化下的架构增益），而非 37.4x。**
> KV 量化对基线帮助更大（基线是 KV 主导），这是必须披露的事实。

**解码优化的优先级（按"减少字节读取"重排）**：

| 手段 | 减字节 | 说明 |
|---|---:|---|
| **MoD / 层跳过** | 50% | 跳过层 = 不读该层权重 ✅ |
| **簇路由输出头** | 70%（头部） | 只读激活簇的权重 ✅ |
| GQA g=8 | 88%（仅 KV 部分） | ⚠️ 只减 KV 权重 |
| 量化 int4 | **75%** | ★ 单项最大，但基线也适用 |
| MoE | — | ❌ 专家切换反而使缓存失效 |

### 000.3 编码轨：stage-0 是地板

级联后：**stage-0 占剩余的 74.1%**。继续优化只能攻击它——**减深度**或**减宽度**。

| 配置 | encode @131K | 省 |
|---|---:|---:|
| v0.8（stem d512, L₀=2） | 558.6 G | — |
| stem d=384 | 377.8 G | 32.4% |
| **stem d=256, L₀=1** | **196.7 G** | **64.8%** |
| + GQA g=8 | 139.6 G | 75.0% |
| d=192 + s1@20%（激进档） | ~94 G | 83% |

### 000.4 ★ 全局预打分通道（本轮最有价值的机制）

**动机**：浅层打分最大的失败是**缺乏全局上下文**——"这段现在看着普通，但后文需要它"。

**方案**：
1. stage-0（窄 d=256）输出后，每块产生 **[MEM] 摘要 token**（256 块 × 8 = 2048 个）
2. 对这 **2048 个摘要做一次全连接全局注意力**
3. 用"看过全局"的表示给段打分、分配 stage-1 预算
4. 再进入 stage-1 / stage-2 深层处理

**成本**：$2 \times 2048^2 \times 256 =$ **2.15 G MACs = encode 的 1.5%**

> **用 1.5% 的成本，给打分器买来全局视野。**

**先例支持**（调研确认这是最有据可依的组件）：
- **NSA**：compression 分支先算块重要性 → 指导 selection 分支选精细 KV ✅ 模式一致
- **Funnel-Transformer**：先压缩，用压缩态作 query，同时保留细粒度 KV ✅
- Hi-Transformer、Set Transformer：先粗后精

### 000.5 逐阶段专家分配

| 阶段 | token 占比 | MoE | 理由 |
|---|---:|---|---|
| stage-0 | 100% | **8选1** | 处理量最大，最该省 |
| stage-1 | 30% | 8选2 | 均衡 |
| stage-2 | **5%** | **8选4** | token 极少，多给专家几乎免费 |

**深层容量几乎免费地拉满**——因为 stage-2 只处理 5% 的 token。

- 若 d=256 在 oracle 下也不可达 → 继续压缩 stem **没有意义**

## 零之零零、v0.8：级联自适应深度编码器

### 00.1 洞察：只留 5%，为什么要算 100%？

我们最终只保留 **5%** 的段作为精确证据。但编码器让 **100%** 的 token 过了 6 层。

成本结构（v0.7，d=512）：注意力 0.4%、FFN 33.2%、**投影 66.4%**——这些钱大部分花在了注定被淘汰的 95% 上。

**学名**：分档全局容量级联深度路由（Stage-wise Global-Capacity Cascaded Depth Routing）。
属 ACT 家族，是 **MoD 的确定性阶段化变体**——不是 early-exit（决策是"停止"而非"深度"），也不是 Funnel（池化不可逆，会破坏证据可追溯性）。

| 对比 | 相同 | 差异 |
|---|---|---|
| **MoD** | 固定容量、全局 top-k、静态图 | MoD 每层独立重选（路由抖动 + gather/scatter）；我们是 2-2-2 阶段、连续深度 |
| **Funnel-Transformer** | 漏斗式预算再投资 | Funnel 沿序列池化（不可逆）；我们保留离散原文证据 |
| **Early exit** | 浅层信号决定后续 | 决策是"停止"；置信度是任务代理，非"是否值得深算"的段证据分 |

### 00.2 收益

| 配置 | encode @131K | 省 | 每 token |
|---|---:|---:|---:|
| v0.7 基线（全部 6 层） | 1,241.3 G | — | 9.47 M |
| **v0.8 级联** | **558.6 G** | **55%** | **4.26 M** |
| + GQA g=8 | 396.2 G | 68% | 3.02 M |
| + 沙漏 384（**高风险**） | 223.3 G | 82% | 1.70 M |

### 00.3 ⚠️ 生死问题：浅层打分准不准？

**这是方案最大的风险，调研给了明确负面证据。**

> DeeBERT 依赖的前几层浅特征和内部分类器 **"not sufficient and reliable"**，同层数下甚至不如微调完整浅模型。（Li et al.）

误差分解：$z_s^{(0)} - \eta_s = b_s + \epsilon_s$

- $\epsilon_s$：无偏噪声，**30% 超额选择可平均掉**
- $b_s$：**选择偏差**，无法通过扩大 30% 消除

最危险的三类 $b_s$：① 长距离桥接段（当前普通，后续需要）② 否定词/数值/边界段 ③ 依赖块间 MEM 路由才建立的关联。

**关键数字**：从 30% 筛到 5%，某类关键段覆盖率只要低于 $5/30 = 16.7\%$，最终证据就系统性受损。

> **30% 挡不是召回保证，只是召回预算。**

### 00.4 必须通过的硬指标

| 指标 | 定义 | 门槛 |
|---|---|---|
| **Stage-1 段召回** | top-30% 对最终 top-5% 的覆盖 | **≥98%**（达不到就扩浅层，不是盲目扩 30%） |
| **最终段召回** | 所选 5% 对 oracle 支持段的覆盖 | **≥95%** |
| **边界召回** | 段边界、否定、数字、实体首次出现 | 不低于随机同长度基线 |
| **桥接召回** | 只在跨块注意后成立的证据 | 按距离分层报告 |

**明确的停止条件**：
- stage-1 召回达不到 98% → 加全局信号/教师蒸馏，**不是继续减到 20%**
- 30% 仍追不上 dense 6 层 → **级联降级为推理时动态 MoD**
- d=384 在同等 FLOP 持续差于 d=512 → 即使理论更省也不采用

### 00.5 容错架构（四条）

1. **双层分数**：stage 0 用 $g_\theta(h^{(2)})$ 粗分，stage 1 用更深 $f_\phi(h^{(4)})$ 精分，共同预测"是否进 5%"。训练标签来自**深层 oracle**，不用下一 token loss。
2. **残差携带被跳过信号**：未入选 70% 的段**不物理删除**，压缩为每块一个"块摘要 latent"供记忆桥交叉注意。
3. **覆盖约束优先于纯分数**：全局 top-30% **之外**，每块至少保 2 个候选 + 罕见 token/表格边界软配额。
   > ⚠️ **30% 必须是"全局竞争 + 块级最低配额"的混合**。若仍是每块各自 top-K，就只是把粗筛边界挪了个位置，没解决密集块漏选。
4. **多阶段一致性监督**：第 4 层的精分预测第 6 层最终选择；stage 翻转率高时增大路由损失。

### 00.6 训练方案

| 阶段 | 内容 |
|---|---|
| ① | 先训 dense 6 层，拿到最终保留 oracle 标签 |
| ② | 冻结主干，训 stage-0/stage-1 打分头（用 oracle 监督，**深层蒸馏**） |
| ③ | 引入软门松弛 + STE，全局容量 top-k（固定形状，非动态） |
| ④ | 课程式收紧预算：50% → 30% → 5% |
| ⑤ | 全链路微调 |

**深度路由器崩溃防御**：选择熵监控、覆盖率监控、块配额下限、stage 翻转率统计。

### 00.7 编码器 GQA 与宽度：不要一次上整包

**GQA 证据**（T5-XXL，编码器—解码器）：

| 配置 | 秒/样本 | 任务分 |
|---|---:|---:|
| MHA-XXL | 1.51 | 47.2 |
| GQA-8-XXL | **0.28** | **47.1** |

GQA-8 只差 0.1 分，速度 5.4x。**但这是自回归 T5 的外推，双向 131K 编码器缺直接证据。**

> 投影占 66.4%，必须**分别报告 Q/K/V/O 的 FLOP**，不能统称"GQA 省 66%"。

**宽度决策**：

| 方案 | 判断 |
|---|---|
| d=512（v0.8 保持） | ✅ 安全，先验证级联 |
| d=448 | 次选 |
| **d=384** | ⚠️ **高风险高回报假设**，无公开消融支持 |

**记忆桥 latent 维度**：$m \ge d$ 起步（不是 $m<d$）。合理关系 $m = d + \alpha B$，$\alpha\in[0,1]$。若 $m<d$，桥接投影会先把保留段的 $d$ 维表示压缩，丢掉级联好不容易保住的细粒度。

### 00.8 解码器：先 head，再 GQA，最后 MoD

| 优化项 | 收益 | 优先级 |
|---|---:|---|
| **Adaptive softmax** | 头 8.36→6.23 M（−25%） | **高**（Grave et al. 报告 2–10x） |
| **Decoder GQA g=8** | self-proj 6.55→3.69 M（−2.87 M） | **高** |
| MoD 50%→65% | 线性增成本 | 中（需质量悬崖监测） |
| 8 层→6 层 | 约 −7.55 M | **后做**（需同等 FLOP 质量验证） |

**Adaptive softmax 实现**：按词频分簇，高频 4000 词直接投影，低频走 $d\to128$。保留完整头的**影子评测**，定期检测长尾/专有名词/代码标识符召回。

> 不建议首选 hierarchical softmax 作为唯一方案——$O(\log V)$ 适合 CPU 时代，现代 GPU 的小矩阵 kernel 开销可能抵消理论收益。

**v0.8 解码：30.2 M → 25.2 M（−17%）**

## 零之零、v0.7：注意力免费后的瓶颈转移（本架构最重要的发现）

### 0.0.1 发现

我一直只算注意力成本。加上 $O(N\cdot d^2)$ 的线性层后，encode 成本的真相：

| 组件（N=131072） | 成本 | 占比 |
|---|---:|---:|
| 段内注意力 $16\times32^2$ | 6.442 G | 0.12% |
| 段间路由 $16^2$ | 0.101 G | 0.00% |
| 打分器 | 0.003 G | 0.00% |
| **FFN $2\cdot d\cdot 4d$** | **3,710.9 G** | **66.6%** |
| **投影 QKV/O $4d^2$** | **1,855.4 G** | **33.3%** |
| **合计** | **5,572.8 G** | 100% |

对照全注意力 prefill（84.7 T）：注意力 79.2 T（93.4%）、线性层 5.57 T（6.6%）。

> **我把注意力省了 12,094x，但线性层一分没省。它现在占 99.9%。**

**这不是设计失误，是稀疏化成功后的必然。** 调研确认：NSA 也观察到 64K 解码时传统 softmax 注意力占 70–80% 时延，优化后瓶颈必然迁移。

**理论交叉点**：标准 Transformer 中线性项 $24Nd^2$ 与注意力 $4N^2d$ 相等时，$N^* = 6d$。对 $d=768$，$N^*\approx4608$。所以长序列下先优化注意力完全正确——但优化完必须回头处理 FFN。

### 0.0.2 ⚠️ 一个必须澄清的口径陷阱

**很多论文报告的是"注意力层加速"，不是端到端加速。**

| 工作 | 报告指标 | 数值 | 口径 |
|---|---|---:|---|
| NSA | **端到端**（同模型对比） | 64K 解码 **11.6x** / 前向 9.0x / 反向 6.0x | ✅ 端到端 |
| MoBA | **注意力层**前向 | 1M prefill 最高 6.5x，10M 减少 16x | ⚠️ 仅注意力层 |
| Kimi Linear | 端到端吞吐 | 1M 解码最高 6x，KV −75% | 混合架构，不可分解 |
| MLA | 吞吐 | 5.76x | — |
| Jamba / Nemotron-H | 端到端 | 3x | — |

> MoBA 的数字是诚实且重要的，但**它的正确比较对象是稠密注意力核，不是完整 prefill**。拿它和 NSA 的端到端数字直接对比是错的。

### 0.0.3 编码器 vs 解码器：必须用不同方案

**这是 v0.7 最关键的设计决策。**

| | 编码器（prefill） | 解码器（batch=1 自回归） |
|---|---|---|
| 瓶颈 | **compute-bound** | **memory-bound** |
| 原因 | 131K token 一次前向，大 GEMM | 每步只算 1 token，但要读全部权重 |
| MoE 有效？ | ✅ **有效** | ❌ **很可能无效** |
| 正确方案 | **MoE 8选2** | **MoD（跳过整层）** |

**算术强度实算（解码器，d=640，8 层，fp16）**：

| 方案 | FLOPs | 权重读取 | 强度 |
|---|---:|---:|---:|
| 稠密 FFN | 26.2 M | 52.4 MB | 0.50 FLOP/byte |
| MoE 8选2 | 6.6 M | 13.1 MB | **0.50 FLOP/byte（不变！）** |
| MoD 跳 50% | 13.1 M | 26.2 MB | 0.50 FLOP/byte |

> **MoE 的 FLOPs 和权重读取同比例下降，算术强度不变。** 而且专家切换会导致缓存失效——**实际可能更慢**。
> 只有 batch 足够大（≥32）时，强度才随 batch 提升，MoE 才恢复有效。

**MoD 的优势**：跳过整层而非切分 FFN，不增加参数量、不引入专家切换、缓存友好。原论文：相同训练 FLOPs 下 log-prob 最多 +1.5%，或损失持平时前向 FLOPs 降低 >50%。

| 2,048 | 81.8 M | 88.0 M | 0.93x |
| **2,718** | 88.0 M | 88.0 M | **1.00x（盈亏平衡点）** |
| 8,192 | 138.4 M | 88.0 M | 1.6x |

### 0.5 记忆层级：不删除，先重构

调研结论：**理论冗余 ≠ 实现冗余**。四级（近期工作集 / 精确凭证 / 演化状态 / 关联事实）功能边界成立，但存在**重复保存、重复路由、重复投影**。

## 一、为什么"只在 encode 阶段"能解掉因果性难题

### 1.1 v0.4 的错误判定

v0.4 认为"全序列全局 top-P 违反因果性，流式不可实现"。这个判定**混淆了两件事**：

| | 是否依赖未来 | 是否可实现 |
|---|---|---|
| 需要**未来块**参与排序 | ✅ 依赖 | ❌ 不可实现 |
| 只与**已见块**竞争预算 | ❌ 不依赖 | ✅ **可实现且精确** |

关键洞察：**选择动作发生在 encode 阶段，但竞争范围只需要"已见集合"**——而这恰恰就是堆能精确维护的。

处理第 1 块时，未来块尚未生成。即使等待完整 prefill，把每个查询对全部段做精确重要性排序仍需 $O(N\log N)$ 或 all-to-all 注意力，**且排序结果会随未来查询变化，不是稳定目标**。

NSA 和 MoBA 都明确采用因果可见集：

- **MoBA**：对未来块设置负无穷门控值，查询只能因果地路由至已见 KV 块
- **NSA**：先由压缩分支计算块重要性，再从中选 top-n 个**完整块**，而非对全部 token 精确排序

### 1.2 实算验证：流式堆 = 全局 top-B（零误差）

维护一个 size-$B$ 的最小堆，新段分数 $s$ 与堆顶比较：

```
if len(heap) < B:      push(s, i)
elif s > heap[0]:      heapreplace(heap, (s, i))
```

**实算（N=131072，4096 段，B=204）**：

| 场景 | 流式堆 vs 全局 top-B 重合度 |
|---|---:|
| 分数与位置无关 | **100.0%** |
| 分数随位置线性上升（趋势 0.5） | **100.0%** |
| 分数随位置强上升（趋势 1.0） | **100.0%** |

**证明**：堆维护的始终是"已见集合的 top-B"。当最后一个段处理完，已见集合 = 全集，堆里就是全局 top-B。**与到达顺序、分数分布、位置趋势完全无关。**

**成本**：1024 个候选 × $\log_2(204)=7.7$ ≈ **7.9K 次比较**。相对块编码的 6.44 G MACs，**完全可忽略**。

> 这推翻了 v0.4 "全局 top-P 不可实现"的结论。v0.4 错在把"全局"理解成"需要未来块"，而实际上**只需要已见块**。

### 1.3 唯一不可消除的损失：未来信息缺失

堆的精确性有前提：**分数在处理时确定且不再更新**。

若某段的重要性依赖后文（如"这段定义的术语在第 50 页被引用"），流式打分时它看起来不重要：

| 依赖后文的关键段占比 | 流式召回 / 离线最优 |
|---:|---:|
| 0% | 100.0% |
| 20% | **76.5%** |
| 40% | **59.8%** |

**这是流式唯一无法消除的信息损失。** 缓解手段：

1. **周期刷新**（每 P=512 重编码）——新上下文会重新打分
2. **L1/L2 补偿**——落选段降级写入，而非丢弃
3. **块摘要保底**——即使原文被淘汰，摘要仍在

### 1.4 ⚠️ 最大的陷阱：禁止块内归一化

如果对每个块独立做分数归一化（常见做法），跨块分数就不可比：

| 打分方式 | 关键段召回 |
|---|---:|
| 全局可比分数 | **38.9%** |
| 每块内归一化 | **6.1%** |

**块内归一化让每个块都"有高分段"，预算被均匀稀释，召回崩塌 6.4 倍。**

→ **打分器必须输出全局可比的分数**：共享权重、无块内归一化、无块级 bias。这一条必须写进代码注释。

### 1.5 块内预筛：top-K_seg=4 是无损拐点

全序列段数太多时，可先做块内预筛再入堆。**但关键事实往往聚集在少数块**，此时预筛会漏：

**关键段均匀分布时**（每块关键段数相近）：

| K_seg | 候选数 | 召回 | vs 无预筛 | 候选压缩 |
|---:|---:|---:|---:|---:|
| 无预筛 | 4096 | 39.8% | 1.00x | 1.0x |
| top-2 | 512 | 39.8% | 1.00x | 8.0x |
| top-4 | 1024 | 39.8% | 1.00x | 4.0x |

**关键段聚集在 20% 块时**（真实场景）：

| K_seg | 候选数 | 召回 | vs 无预筛 |
|---:|---:|---:|---:|
| 无预筛 | 4096 | 27.9% | 1.00x |
| top-1 | 256 | 7.0% | **0.25x** |
| top-2 | 512 | 14.0% | **0.50x** |
| top-3 | 768 | 21.0% | **0.75x** |
| **top-4** | 1024 | **27.9%** | **1.00x** |
| top-6 | 1536 | 27.9% | 1.00x |

> **K_seg=4 是拐点**。$K_{seg} < 4$ 时，密集块里的关键段会被块内截断直接砍掉——**且堆无法补救，因为它们根本没进候选集**。

**推荐 $K_{seg}=4$**（候选压缩 4x，聚集场景无损）。若要更保守用 6。

**动态配额**（冷块 top-1、热块 top-8）可把候选压到 613（6.7x）且无损，但需要预算网络准确预测热块——**这是可选加速，不是必需**。

### 1.6 方案对比

| 方案 | 流式可行 | 精确性 | 成本 | 角色 |
|---|---|---|---|---|
| **已见段最小堆** | ✅ | **精确（零误差）** | $O(\log B)$/候选 | **主推荐** |
| 块内 top-K_seg=4 + 堆 | ✅ | 精确（$K\ge4$ 时） | 候选压缩 4x | **推荐** |
| 动态配额 + 堆 | ✅ | 依赖预测准确度 | 候选压缩 6.7x | 可选加速 |
| 8 桶计数 / CMS | ✅ | 有哈希误差 | $O(1)$ | 仅粗筛 |
| H2O 重击者 | ✅ | 次模近似 | $O(1)$–$O(\log B)$ | 辅助信号 |
| 两遍全序列 | prefill ✅ / 生成 ❌ | 不等于全局 | 约 2x | prefill 可选 |
| 蓄水池 / 指数衰减 | ✅ | 无竞争比保证 | $O(1)$ | 兜底 |

### 1.7 Encode 阶段的完整流程

```
┌─ ENCODE (每个块) ─────────────────────────────────────────┐
│ 1. 段内注意力 16×32²    → 段表示                            │
│ 2. 段间 MEM 路由 16²     → 跨段交互                          │
│ 3. [MEM] 块摘要          → 必留, 不占精确预算                 │
│ 4. 打分器 (全局可比!)    → 每段的分数 s_b                    │
│ 5. 块内 top-K_seg=4      → 候选集                            │
│ 6. 候选入最小堆 (size B) → 与已见段竞争预算                   │
│    被淘汰的段 → 降级写入 L1/L2 (不丢弃!)                     │
└───────────────────────────────────────────────────────────┘
                          ↓
┌─ DECODE (每 token) ───────────────────────────────────────┐
│ 零选择。只读固定的 960 个 key:                              │
│   L0 摘要 512 + L1 波 64 + L2 粒子 256 + L0.5 证据 128      │
│ (L0.5 的 top-128 是注意力 softmax 的自然行为, 非选择操作)     │
└───────────────────────────────────────────────────────────┘
```

> **关于 L0.5 的 top-128**：这是从"已入选的证据池"里做注意力检索，softmax 本身就是软性 top-k，**不违反"encode-only 选择"的约束**。真正的"选择哪些 token 进入证据池"完全在 encode 阶段完成。

| $C$, overlap | 512, 64 | 块大小 / 重叠 | 未变 |
| $S$, $n_{seg}$ | 32, 16 | 段大小 / 每块段数 | 未变（S=16 备选） |
| $m$ | 8 | 每块摘要 token | 待消融 |
| $W$ | 128 | 局部窗口（处理时，不持久化） | 未变 |
| **$K_{seg}$** | **4** | **块内预筛（无损拐点）** | **v0.5 新增** |
| **$B$** | **204 段当量（5%）** | **全局精确预算（堆容量）** | **v0.5 明确** |
| **堆** | 最小堆 | **已见段竞争，零误差** | **v0.5 新增** |
| $R$ / $M$ / $K$ | 64 / 64 / 256 | L0 / L1 / L2 | 未变 |
| $P$ | 512 | 周期刷新 | 未变 |

### 1.9 top-p 在 encode-only 下的定位

**top-k 是预算锚点，top-p 是候选自适应。**

| 用途 | 机制 | 理由 |
|---|---|---|
| **全局预算 $B$** | **top-k（固定 204）** | 堆容量必须固定；容量 = 状态预算 |
| 块内候选 $K_{seg}$ | top-p（累积 0.9）或固定 4 | 候选数可浮动，不影响状态预算 |
| decode 检索 top-128 | 注意力 softmax | 软性 top-k，非选择操作 |

> top-p 的动态 $k$ 在批处理时需要 padding 或固定桶，且**累积概率 ≠ 重要性**。因此它只适合放在"候选生成"这一层，不能承担预算管理。

## 二、保留等级：从二值扩展为四档多精度

### 2.1 离散 KKT 最优不是二值

设段 $b$ 获得 $k_b \in \{0,1,\dots,K_{\max}\}$ 个单元，收益 $R_b(k_b)$ 严格递增：

$$
\max_{\{k_b\}} \sum_b R_b(k_b) \quad \text{s.t.} \quad \sum_b k_b \le B
$$

若 $R_b$ 可微严格凹且 $k_b$ 连续，最优条件为**边际收益相等**：

$$
\frac{\partial R_b}{\partial k_b}\bigg|_{k_b^\star} = \lambda \quad (0 < k_b^\star < K_{\max})
$$

连续 water-filling 解：$k_b^\star = \text{clip}\big(R_b''^{-1}(\lambda), 0, K_{\max}\big)$。

> **"全局统一 sigmoid 阈值"等价于用单个阈值比较全部段，只有在各段收益函数相同且尺度一致时才可能接近最优。** 这是 v0.3 打分设计的理论缺陷。

### 2.2 四档设计

$$
q_b \in \{0,1,2,3\},\qquad \sum_b c(q_b) \le B,\quad c(0)<c(1)<c(2)<c(3)
$$

| 档 | 内容 | 代价 | 收益边界 |
|---|---|---:|---|
| 0 | 仅摘要 / 指针 | 0 | $R_b(1)-R_b(0)$：摘要是否足够 |
| 1 | 低精度 latent / KV | 0.15 | $R_b(2)-R_b(1)$：低精度是否充分 |
| 2 | 混合精度关键段 | 0.45 | $R_b(3)-R_b(2)$：是否需完全精确 |
| 3 | 完全精确原文 | 1.0 | — |

**执行顺序**：① 必须保留集分配 $\text{minK}_b$ → ② 剩余预算按边际收益竞争 → ③ 连续松弛 + 整数补丁。

**实算（贪心实现边际收益相等，预算 5%）**：

| 策略 | 总覆盖 | 高密覆盖 | 低密覆盖 | 加权信息保留 |
|---|---:|---:|---:|---:|
| 二值（全给精确档） | 5.0% | 100% | 0% | 6.1% |
| 多精度（纯贪心） | 15.2% | 100% | 0% | **10.4%（1.70x）** |

**多精度在加权信息保留上优于二值 1.70x**——因为低档能兜住大量中等价值段。

### 2.3 一个必须承认的发现：5% 预算下 min-K 保底不可能

```
总段数 4096, 精确预算 204 段当量 -> 平均每段 0.050 段当量
  c=0.15  需要 614.4 段当量   预算不足
  c=0.05  需要 204.8 段当量   预算不足   ← 差一点点
  c=0.01  需要  41.0 段当量   可行
```

**5% 预算下无法给所有段任何有意义的非零保底。**

→ **保底必须来自"不占预算的层"**：块摘要（1.56%）+ L1/L2（$O(1)$）。

这反过来证明了**L1/L2 不是可选优化，而是架构必需**——它们是唯一能提供全覆盖保底、且不随序列长度增长的层。

### 2.4 完整状态预算（N=131072, fp16）

| 层 | 单元 | 状态 | 占比 |
|---|---:|---:|---:|
| ① 块摘要（全序列 8/块） | 2,048 向量 | 6.00 MB | 1.56% |
| ② L1 波记忆 | 64 slot | 0.19 MB | 常数 |
| ③ L2 粒子槽 | 256 KV 槽 | 1.50 MB | 常数 |
| **固定层小计** | | **7.69 MB** | |
| ④ 精确证据 2% | 2,621 tok | 7.68 MB | 总 15.4 MB / 28x |
| ④ 精确证据 **5%** | 6,553 tok | 19.20 MB | **总 26.9 MB / 15x** |
| ④ 精确证据 10% | 13,107 tok | 38.40 MB | 总 46.1 MB / 9x |

对照：全注意力 @131072 = **384 MB**。

## 三、打分信号：六信号融合 + 反事实监督

### 3.1 没有单一信号可靠

| 信号 | 可计算公式 | 实证 | 失效模式 |
|---|---|---|---|
| 累计注意力 | $a_b=\sum_{l,h,t\le T}\text{Attn}_{l,h,t,b}$ | H2O：20% heavy-hitter 约 **29x** 吞吐 | **只看过去**；attention sink 与高频共现被高估 |
| 观察窗投票 | $c_h=\sum_{i\in W}q_{h,i}k_h^\top$ | SnapKV：16K 约 **3.6x** 速度、**8.2x** 内存 | 需未来查询；不同指令会改变重要键集合 |
| surprise / 梯度 | $u_t=\|\nabla_{x_t}\ell_{\text{assoc}}\|$ | Titans：BABILong 优于对比系统 | 高 surprise 可能是噪声；未证明与未来需求因果相关 |
| 重建误差 | $\|\text{Attn}(Q,K,V)-\text{Attn}(Q,\tilde K,\tilde V)\|_F^2$ | KIVI 报告 KV 重构误差 | 保护当前计算图，**不保证保护未来答案** |
| 语义新颖性 | $\min_m \text{dist}(z_b, z_m)$ | LLMLingua：最高约 **20x** 压缩 | 可能把局部连贯误判为冗余 |
| 位置先验 | $\alpha\mathbf{1}[\text{first}]+\beta\gamma^{\text{pos}}$ | StreamingLLM：稳定至 **400 万** token | 保底，非内容理解 |

**关键区分**：这些是**特征**（当前可算），不是**标签**（未来才知）。把它们当标签就是"伪可学习性"。

理想目标是边际贡献：

$$
\Delta_b = \ell(Y \mid \mathcal{H}_{-b}) - \ell(Y \mid \mathcal{H}_{-b} \cup \{x_b\})
$$

### 3.2 训练监督：反事实标签 + 可微松弛 + 课程

**不能用纯 RL。** 推荐路径：

1. **构造反事实标签**：同一段保留 vs 删除后的 LM/检索损失差 $\Delta_b$
2. **可微松弛**：Gumbel-Softmax / 确定性 top-K / STE
3. **课程**：先密集监督（重建误差）→ 再稀疏下游信号
4. **推理时**：硬预算

> H2O、SnapKV、IndexMem、LU-KV 都证明中等压缩比下启发式已实用，**但没有证据表明它们在 5% 极端预算下长期稳定**。

#### ⚠️ 反事实标签的代价必须先压缩

精确 $\Delta_b$ 需要 **$B+1$ 次完整前向**（$B$ = 段数），不能直接用于预训练。

**降本路径**：
1. **共享完整前向**：一次前向拿到所有段的表示，再对每段做一次局部重算
2. **一阶/随机影响近似**（influence function 的 Hessian 近似、TracIn、梯度累积）
3. **分层 chunk 课程**：先在短 chunk 上算精确 $\Delta_b$，再外推
4. **重要性采样**：只对高分/边界附近的段算精确值
5. **周期性金标准**：用同查询多 rollout + 真实 leave-one-out 校准近似

#### ⚠️ 不要从零端到端训练打分器

调研的核心警告：

> **可学习打分器能 work，但"对任意 4K–128K 上下文直接端到端学到仅 5% 黄金证据"目前既无足够正面证据，也不是可直接迁移的成熟范式。**

现有成功案例主要在**层内 token 剪枝、动态计算分配、chunk 检索**——不是"16-token 段 + 全局 top-5% + 延迟因果监督"这种极端设定。

**正确做法：强启发式兜底 + 反事实/任务损失微调 + 多保底分层保留**
- 先建立强启发式并集（六信号全用），作为不可击穿的下限
- 学习器只学**残差修正**，不是从零决策
- 只有学习器在多个课程阶段稳定超过启发式并集、逼近 oracle，才关闭确定性保底

#### 训练课程（三阶段）

| 阶段 | 内容 | 目标 |
|---|---|---|
| **① 稠密监督** | 冻结强启发式，在可验证任务（MQAR/passkey）上学融合残差与校准 | 学到有意义的融合权重 |
| **② chunk 课程** | 多预算课程（20%→10%→5%），逐步收紧 | 建立容量意识 |
| **③ 段级微调** | 微调整个打分器 + 硬 top-204 | 对齐执行行为 |

**诊断指标**（判断打分器是否真学到了东西）：
- oracle 召回（对已知关键集的 Recall@5%）
- 最坏损失（worst-case loss，不只是平均）
- 路由稳定性（跨 batch/跨长度的分段选中一致性）

### 3.3 落选段的处理：降级而非丢弃

**硬保留会把排名误差转化为不可逆失真。** 被 top-K 拒绝的段不应丢弃，而应：

- 降级为档 1/档 2（低精度）
- 写入 L1 波记忆或 L2 粒子槽
- 保留指针，需要时可触发重新提升

> 这与 IndexMem 的 "indexer + latent memory residual" 一致。收益是显著降低永久遗忘风险；代价是解码器需承担多源读取与冲突控制。

## 四、块内架构：段间必须升级

### 4.1 段大小的选择

| $S$ | 段数 | 段内 | 段间 | 合计 | 省 | **段间占比** |
|---:|---:|---:|---:|---:|---:|---:|
| 16 | 32 | 12.58 M | 1.57 M | 14.16 M | **28.4x** | **11.11%** |
| **32** | 16 | 25.17 M | 0.39 M | 25.56 M | 15.8x | **1.54%** |
| 64 | 8 | 50.33 M | 0.10 M | 50.43 M | 8.0x | 0.19% |

**S=32 时段间只有 16 个向量做全连接，容量严重不足（占 1.54%）。**

→ **段间必须从朴素全连接升级为可学习 MEM 路由**（压缩 MEM 或低秩路由）。
→ **S=16 是更好的备选**：更省（28.4x）且段间容量翻倍（32 个向量，占 11.11%）。

> 口径说明：本文统一 $2L^2 d$（含 QK 与 AV、含 $d$）。调研报告按"忽略 $d$"口径算得 24.2x，但比例一致（402.65/25.56 = 262144/16638 = 15.75）。

### 4.2 纯 Mamba 不做块内主力

| 方案 | MACs | 判断 |
|---|---:|---|
| 两级段处理 S=32 | 25.6 M | 基准 |
| 两级段处理 S=16 | 14.2 M | 更优 |
| 纯 Mamba-2 块扫描 | 约 8.4 M（$P=64,d_h=128$） | **不可仅按 token 数比较** |
| Gated DeltaNet 块并行 | 约 537 M（$B=64$） | 不自动低于两级注意力 |

→ **纯 SSM 只在块间记忆与跨块因果传递上有明显优势**，不适合替代块内的段级精确选择。

## 五、硬件对齐：真实加速预期

### 5.1 NSA 实测数据（不可直接外推）

| 场景 | 加速 |
|---|---:|
| 64K prefill 前向 | 9.0x |
| 64K 解码 | **11.6x** |
| 反向 | 6.0x |

**NSA 内核的三个要点**：
1. 路由器按 **GQA 组聚合**（同组共享稀疏 KV 块索引）
2. 被选块至少包含 **64 个连续 token**（GPU 连续访存 + Tensor Core 利用率）
3. 查询—块对通过 **varlen FlashAttention** 执行

NSA 减少的主要是**解码期的内存访问**，不是单纯减少 MACs。

### 5.2 HRC-LLM 的保守预期

> **把 15.8x 视为理论上限，现实目标是 3–7x。**

前提条件：① 被选段形成连续块 ② 同一 GQA 组共享路由 ③ Flash/Triton fused kernel。

**执行顺序**：
```
1. 用压缩向量算块级分数
2. torch.topk 取 K 个块
3. 扩展前后 halo 维持段连续性
4. 合并相邻块 ID 为大区间
5. 对每个 (q_group, block_interval) 调用一次 varlen kernel
```

> `torch.topk` 文档未承诺近似算法或大 $k$ 的性能，不能假设它天然适合超大序列。

## 六、评测指标必须更换

**"关键段幸存率 16.66%"不是一个好指标**：

- 它既不是 Precision，也不是端到端任务损失
- 多精度下"精确幸存率"会下降，但**加权信息保留反而上升**
- 理论连续最优（严格凹假设）在 5% 预算下约 **30%**，当前 16.66% 只有其 55%

**应同时报告**：

| 指标 | 含义 | 不能推出什么 |
|---|---|---|
| Recall@5% | 精确段中恢复了多少 oracle 关键段 | 不能推出端到端无损 |
| Precision@5% | 被选中段有多少确实关键 | 不能反映摘要/残差的补偿作用 |
| **任务损失差** | 压缩后相对完整上下文的 LM/QA 损失 | 需要完整上下文 oracle |
| **反事实损失差** $\Delta_b$ | 保留 vs 删除的损失差 | 不能直接替代在线未来奖励 |

## 七、设计红线

| # | 禁止 | 理由 |
|---|---|---|
| 1 | **选择逻辑泄漏到 decode 阶段** | v0.5 的核心约束；decode 必须零选择、恒定成本 |
| 1b | **从零端到端训练打分器（5% 硬截断）** | 无正面证据；必须强启发式兜底 + 残差学习 |
| 1c | **每层都做 960-key cross-attention** | 只在 1/3/6/8 层做，省 13% |
| 1e | **解码器用 MoE** | batch=1 是 memory-bound，算术强度不变且缓存失效；用 MoD |
| 1f | **只算注意力成本就报告加速** | 线性层占 99.9%；必须端到端口径 |
| 1g | **拿 MoBA 的注意力层数字与 NSA 端到端数字对比** | 口径不同，不可比 |
| 1h | **把周期重编码做成滑动窗口** | 会变成 $O(NP)$；必须编码新增 token |
| 1i | **一次性上"级联+GQA+d=384"整包** | 无法归因；d=384 是高风险假设，先验证级联 |
| 1j | **30% 容量用每块固定 top-K** | 重现密集块漏选；必须全局竞争 + 块级最低配额 |
| 1k | **认为 30% 挡是召回保证** | 它只是召回预算；覆盖率 <16.7% 就系统性受损 |
| 1l | **stage-1 召回不达标时盲目扩大 30%** | 应扩浅层表示/加教师，不是侵蚀 FFN 节省 |
| 1m | **未入选段物理删除** | 应压缩为块摘要 latent 供记忆桥读取 |
| 1n | **用 MACs 衡量解码成本** | 解码是带宽受限（0.21 FLOP/byte），必须按字节 |
| 1o | **把 37.4x 当作架构收益报告** | 对等量化下是 23.5x；量化收益不可重复相乘 |
| 1p | **解码器继续做 FLOPs 优化** | 带宽受限下只有减字节有效（MoD/簇路由/量化） |
| 1q | **stage-0 保持 d=512** | 它占剩余 74.1%，是地板 |
| 1r | **静态蒸馏打分后直接裁剪 stem** | 必须联合训练：窄stem + 上投影 + 全局预打分 + 路由标签 |
| 1s | **继续把编码器当主要优化对象** | 交叉点 M*=24.6，M>25 时解码主导 |
| 1t | **把自投机的 2.30x 当既定收益** | 依赖 α=0.75，必须实测；α=0.5 时只有 1.48x |
| 1u | **认为自投机对所有场景有效** | 纯检索（M<25）只 +1.04x，编码仍是瓶颈 |
| 1v | **在 batch≥32 时仍期待自投机大幅收益** | 大 batch 下权重已摊销，收益显著下降 |
| 1w | **用解码器前 2 层作投机草案** | 29.1 MB，带宽受限下 0.84x 负收益；用 EAGLE 特征 head |
| 1x | **场景公式只算 prefill 的 encode** | 周期刷新使长生成场景低估 10–19x |
| 1y | **假定 45.9 MB 权重可驻留 H100 L2 得 ~10x** | 占 L2 91.8% 属临界；KV 必须走 HBM；上限仅 1.62x |
| 1z | **认为 L2 命中与投机收益可相乘** | 两者都减权重读取，部分重叠 |
| 1aa | **把自适应刷新率应用到 prefill** | prefill 必须完整编码；只对生成 token 生效 |
| 1ab | **只与 MHA 对比 KV 存储** | GQA/MLA 也压 KV，优势从 89x 降到 11x/5.6x |
| 1ac | **只报告单请求延迟** | 真正的价值是缓存密度与并发（服务能力） |
| 1ad | **把激活预算当成写入预算对标** | Quest 1%/NSA 7.81% 是激活（全 KV 保留）；HRC 是永久压缩 |
| 1ae | **沿用 v0.4 拍脑袋的 5% 写入预算** | 记忆桥只 3.86 MB，有巨大余量；默认 15% |
| 1af | **把写入量与激活量绑成一个数字** | 应解耦：写入保召回，激活保带宽 |
| 1ag | **认为多文档记忆可直接拼接** | 需写入门控、淘汰、路由隔离、记忆编辑 |
| 1ah | **把保留决策做成二值（留/不留）** | 精度是连续量；用三级金字塔 |
| 1ai | **给低精度段也跑深层编码** | 精度与深度必须对齐，否则浪费算力 |
| 1aj | **用单一凹价值函数做 KKT 分配** | 精确检索是阶跃的，会解出"0 个满精度段" |
| 1ak | **认为 T2/T3 能兜底精确检索** | 压缩不可逆，精确能力只由 T1 决定 |
| 1al | **粗筛取 top-1%** | 必须过度召回（top-5%），recall@128 ≥ 99% |

## 八、继承 v0.2/v0.3 的未变结论

1. **必须有精确检索路径** —— FDM：纯 scan MQAR 0.011 → 加槽 0.966
2. **forget gate 不能固定 +1** —— 小随机初始化 + 结构性偏置，可训练
3. **重建损失用 attention-reconstruction**，梯度停止回传主干
4. **L2 用 multi-slot 软写入 + 显式擦除**，禁止 one-hot top-1
5. **解码器不低于 15% 参数** —— FutureMind：14B 教师教 7B 优于 72B
6. **段落课程以"段数"推进**，判据是准确率停止改善
7. **评测分轨**：RULER / MRCR / MQAR / LongBench v2
8. **top-k 是训练主目标，top-p 只作预算上限**

**待消融假设**：$m=8$、$K=256$、$P_{glob}=5\%$、$S\in\{16,32\}$、四档代价 $\{0,0.15,0.45,1.0\}$。

class EncodeOnlySelector:
    """
    ENCODE 阶段执行全部选择; DECODE 阶段零选择。
    核心: 已见段最小堆 == 全局 top-B, 零近似误差, 且与到达顺序无关。
    实测成本: 1024 候选 x log2(204) ≈ 7.9K 次比较 (相对 6.44G MACs 可忽略)
    """
    def __init__(self, budget, k_seg=4):
        self.B = budget; self.k_seg = k_seg
        self.heap = []            # (score, seg_id), 最小堆, size <= B
        self.evidence = {}        # seg_id -> 保留档位

    def encode_block(self, seg_scores, block_id):
        """块编码完成后调用。seg_scores: [n_seg] —— 必须全局可比!"""
        # ① 块内 top-K_seg 预筛 (K_seg=4 是聚集场景的无损拐点)
        k = min(self.k_seg, len(seg_scores))
        topk = torch.topk(seg_scores, k).indices.tolist()
        # ② 与已见段竞争预算
        for j in topk:
            gid = block_id * len(seg_scores) + j
            s = float(seg_scores[j])
            if len(self.heap) < self.B:
                heapq.heappush(self.heap, (s, gid))
            elif s > self.heap[0][0]:
                _, evicted = heapq.heapreplace(self.heap, (s, gid))
                self.demote(evicted)      # 降级写入 L1/L2, 不丢弃!
        return self.heap

    def demote(self, seg_id):
        """被淘汰的段: 降级为低精度 / 写入 L1 波记忆或 L2 粒子槽"""
        self.evidence[seg_id] = 0         # 档 0: 仅摘要 + L1/L2 残差

    # ⚠️ 禁止: 块内归一化。会让召回从 38.9% 崩到 6.1%
    # def _normalize_in_block(self, s): return (s - s.min()) / (s.ptp() + 1e-9)  # 禁用!


class CausalBudgetAllocator(nn.Module):
    """可选加速: 预测每块密度 -> 动态 K_seg。非必需, 堆本身已精确。"""
    def __init__(self, cfg):
        self.net = nn.Sequential(
            nn.Linear(cfg.d_enc * 3, 256), nn.GELU(), nn.Linear(256, 1)
        )
    def forward(self, block_summary, hist_summary, rolling_stats):
        """输出该块的 K_seg (1..8)。预测失败会漏关键段, 故默认取保守值 4"""
        x = torch.cat([block_summary.mean(1), hist_summary, rolling_stats], -1)
        return 1 + 7 * torch.sigmoid(self.net(x))


class MultiPrecisionSelector(nn.Module):
    """四档多精度 + 反事实监督 + 边际收益贪心"""
    COST = {0: 0.0, 1: 0.15, 2: 0.45, 3: 1.0}   # 段当量

    def score(self, seg_repr, attn_acc, surprise, recon_err, novelty, pos):
        """六信号融合 —— 特征是输入, 不是标签"""
        return (self.w1 * attn_acc + self.w2 * self.obs_vote(seg_repr)
                + self.w3 * surprise + self.w4 * recon_err
                + self.w5 * novelty + self.w6 * pos)

    def allocate(self, scores, budget, min_k=0):
        """边际收益贪心 —— 离散实现 KKT 条件 dR/dk = λ"""
        q = torch.full_like(scores, min_k, dtype=torch.long)
        remaining = budget - min_k * len(scores) * self.COST[1]
        while remaining > 0:
            gains = self.marginal_gain(scores, q)      # R(q+1) - R(q)
            costs = torch.tensor([self.COST[int(x)] for x in q])
            eff = gains / (costs + 1e-6)
            b = eff.argmax()
            if remaining < costs[b]: break
            q[b] += 1; remaining -= costs[b]
        return q

    def marginal_gain(self, a, q):
        """严格凹收益 R(q) = 1 - exp(-a*q)"""
        return torch.exp(-a * q) - torch.exp(-a * (q + 1))


class SelectiveBlockEncoder(nn.Module):
    """ENCODE 阶段: 段内 -> 段间 -> 打分 -> 块内预筛 -> 全局堆竞争"""
    def __init__(self, cfg):
        self.seg = cfg.SEG; self.nseg = cfg.C // cfg.SEG
        self.seg_encoder = nn.TransformerEncoder(...)   # 段内 S^2
        self.seg_router  = MemRouter(cfg)               # 段间: 可学习 MEM 路由
        self.scorer      = MultiPrecisionSelector(cfg)  # 六信号融合
        self.selector    = EncodeOnlySelector(cfg.B, k_seg=4)

    def forward(self, blocks, block_id):
        b, n, C = blocks.shape
        x = self.emb(blocks.view(b * n, C))
        segs = x.view(b * n, self.nseg, self.seg, -1)
        seg_repr = self.seg_encoder(segs).mean(2)        # [b*n, nseg, d]
        seg_repr = self.seg_router(seg_repr)             # 升级: 非朴素全连接

        # 打分: 全局可比, 禁止块内归一化
        s = self.scorer.score(seg_repr, ...)             # [b*n, nseg]
        # encode-only 选择: 块内 top-4 预筛 + 已见段堆竞争
        self.selector.encode_block(s[0], block_id)

        q = self.scorer.allocate(s, self.selector.B)     # 四档多精度档位
        rejected = seg_repr[q == 0]                      # 降级而非丢弃
        return dict(summary=..., evidence=self.pack(seg_repr, q),
                    rejected=rejected)                   # -> 写入 L1/L2
