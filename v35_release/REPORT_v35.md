# OpenASH v3.5 架构迭代报告：衰减最大值三通道混合架构

**结论**：同预算（15000 步 × 184M tokens、95-105M 参数）下，v3.5 在全部 7 个上下文长度上超过同预算现代 Transformer 基线（RoPE + RMSNorm + SwiGLU + FlashAttention），总体 PPL 领先 10.7%，2048 长度区领先 58.5%，同时保持 O(S) 训练复杂度与 O(1) 推理状态。

---

## 1. 架构概要

v3.5 的每层注意力由**三条 O(1) 状态通道**混合构成，全部基于每层专属的低秩状态嵌入 `state_em(23004×64) @ state_proj(64→768)`（c 流，一次查表三处复用）：

| 通道 | 递推 | 检索类型 | 记忆尺度（实测） | 作用 |
|---|---|---|---|---|
| 快 max-scan | `e_j = max(γ_j·e_{j-1}, c_j)`，γ = exp(−softplus(c·v+b)) | query 无关（新鲜峰值跟踪） | 半衰期 ~4 tok | 局部信号、整体质量 |
| 慢 max-scan | 同上，γ ∈ [0.995, 0.9995]（层 6-11） | query 无关（长时保持） | 半衰期 ~245 tok | 远程信息保持、长度外推 |
| KV 检索 | `S_j = a_j·S_{j-1} + β·k̂_j⊗c_j`，读出 `r_j = q_j·S_j` | **query 相关**（k̂ L2 归一化） | a≈0.98 可学习 | 归纳头/精确键值召回 |

三通道输出在 gen_model 多项式融合（Triton kernel）：`head(cat[a,b,c,d,e])·e + a·b + α₁·b + α₂·d + a·(α₃·e+d) + b·(c+e) + c·e + kv_gate·r`。

配套现代化：pre-norm RMSNorm ×2、SiLU-GLU FFN、final RMSNorm、max_seq_len=2048、分层多尺度 γ 初始化（v3.3）。

## 6. 工程实现要点

- **训练 297 ms/step**（bf16 autocast，bs=32×S=384；KV Triton 前向 0.42 ms/层 + torch 重算反向 4.3 ms/层）
- **O(1) 双状态增量推理**：state 元组携带 `(max-scan e 向量, KV 矩阵 S)`；fp32 下逐 token 解码 vs 全序列前向 diff = 3.7e-06
- **显存**：训练峰值 12.4 GiB（bs=32），DecayScanFn 系数反向重算省 1.8 GB
- **稳定性发现**（重要）：本环境 Triton 对"循环携带累加寄存器 + 循环出口 store"存在 codegen 非确定性（miscompilation 嫌疑）；**循环内逐步 store 模式完全稳定**——所有 kernel 遵循该模式设计，多形状 × 多次发射零漂移验证
- **数值安全**：max-scan 无除法；KV 分块权重 `C[j,i] = exp(l_j − l_i)` 因果掩码后 ≤ 1，无除法无下溢

## 8. 边界与后续方向

1. 验证尺度为 488M tokens / 96-105M 参数——相对真实 LLM 预训练仍小；更大规模需扩展算力
2. delta-rule 分块（UT/WY 变换）与 KV scan 手工 Triton 反向是明确的下一级优化（当前 delta 逐步版不可训练、重算反向 ~4.3 ms/层）
3. gap=128 中距检索仍落后 tf（+0.25 vs +0.62 @3000 步版；大数据版 gap=128 已反超）——delta 写入预期进一步扩大优势
4. tf 基线未做位置外推适配（YaRN/插值）；v3.5 的长度无关性为架构自带
5. 速度上 KV 通道为 max-scan 的 ~15× 单 token 成本，Triton 前向已回收大头；进一步可做 KV 瘦身（dh 减半）消融

## 11. v3.7 短卷积 + 15000 步等预算五模型对决（2026-11-08）

### v3.7 架构（当前最优 v3.x 配方）

在 v3.6（delta 写入）之上新增 **depthwise 因果短卷积**（kernel=4，per-channel SiLU 门控，pre-norm 分支内、注意力前）——GDN/DeltaNet/Mamba 的标配组件，为线性架构补上窗口内精确 n-gram 匹配能力。参数 101.3M（v35 104.8M / tf 95.5M / GDN 106.3M，±10% 内）。

```python
xc = conv1d(xn.transpose(1,2))[:, :, :S].transpose(1,2)   # 左 pad 因果
xn = xn + silu(xc) * (1 + conv_gate)                       # per-ch 门控残差
```

### 缩放确认（6000 步，等 token 73.9M）

v37 18.53 vs v35 19.41（**−4.5%**）——短卷积收益随训练量增大显现（3000 步时两者几乎持平的 delta 已被 v3.6 吸收）。

## 12. v3.8/v3.9：β 门控与自研 delta-rule（2026-11-08）

### v3.8：GDN 式 per-token β（归档，未采纳）

β_t = sigmoid(w_h·k̂_t + b_h)，W 零初始化（起点等价常数 β=0.88）。**3000 步结果：23.46 vs v37 23.45——持平**。机制：kv_gate 零初始化把整个 KV 通道输出早期静音，β 梯度被 kv_gate 阻断——训练 40000 步后 per-head 常数 β 也几乎未移动（raw 3.4-4.2，即 init 4.0 原地）。结论：β 通道在当前架构中不是瓶颈，per-token β 与 β-init 扫描均无短期收益；若未来让 kv_gate 预热更快或 β 直接进主通路，可重测。

### v3.9：自研分块 delta-rule（去 FLA 训练依赖 + 精确 O(1) 解码）

**两次手工 Triton WY 失败的替代路径**：观察到本仓库 T=384/BT=64 → NT 仅 6 个 chunk——纯 torch 分块实现（autograd 免费反向）完全可行，无需手工 Triton 反向。`delta_chunk.py` 逐行锚定 FLA `chunk_delta_h/wy_fast/chunk_fwd/chunk_o` 四文件。

**正确性**：`test_delta_chunk.py` 全 PASS——4 种形状前向（o/S 终态误差 ≤3e-4，fp32 求和序噪声级）+ 初态支持 + 反向五梯度（dq/dk/dv/dg/dβ vs FLA 手写 Triton 反向 ≤1e-3）。

**三个关键约定修正**（对照 FLA 源码 + 2-token 手推双重确认）：
1. **WY 逆 = (I + L)⁻¹（正号）**：chunk 内 delta 覆盖的修正是加法复合（k₂S₁ 含 write₁ 中的 −βkS 项二次翻号），非论文转置布局下的 (I−L)⁻¹
2. **L 仅乘行 β**：`chunk_scaled_dot_kkt_fwd` 的 β_s 只乘行；列 β_t 在 w=A@(βe^g·k)、u=A@(βv) 构造时才进入
3. **输出全局 scale = K^−0.5**：chunk_fwd_o 对 inter+intra 同乘（本仓库 v3.6+ 训练一直隐含此缩放）

**速度**：与 FLA 同量级（fwd+bwd 计时在 GPU 共享时 50 vs 54 ms），训练路径 ~2-4× 慢于 FLA 融合 kernel（符合预估：NT=6 循环的 kernel-launch 开销）；FLA 保留为快速路径，`kv_backend='delta_chunk'` 为去依赖备选。

### v3.9 附带修复：v3.7+ 增量解码三处 bug（全长度 fp32 验证）

修复前 v37 逐 token vs 全序列 logp 差 2.96（v35 无卷积参照 4.29e-06 精确）：
1. **短卷积解码缺状态**：conv 感受野需前 k−1=3 个 token 的 xn——状态元组扩展为 (e, S, conv_buf)（每层 +3×768 数值，仍严格 O(1)）
2. **conv tap 对齐**：解码输出索引应为 len(cat)−1（最新 token 对应最后一个 kernel tap w₃），全缓冲时恰好等于 k−1 掩盖了早期短缓冲的错位
3. **delta 单步语义**：旧版对 delta 模型误用 sum 写入；正确公式 **S ← a·S + k⊗(β·k − β·a·(kS))**（衰减在读出前应用，系数 β·a 非 β²），读出补 K^−0.5 缩放

修复后：**vs 自研 fp32 参考精确到 2.1e-05**（vs FLA 全序列 7e-03 为 FLA kernel tf32 噪声上限）。

### Harness bug 记录（教训）

`FlaLMWrapper.forward_loss(ids, targets)` 曾把 `targets=ids[1:]` 直接作为 `labels` 传给 HF CausalLM——HF 内部再做一次 shift（`logits[t] ↔ labels[t+1]`）导致双重位移，模型实际优化"从 ≤t 预测 t+2"的 2-ahead 目标。修复：labels 右滚一位（`labels[t+1] = targets[t]`）。裁决实验：同一窗口上 `out.loss == CE(logits[t], labels[t+1])`（=1.7335）而非 `CE(logits[t], labels[t])`（=8.99），铁证 HF 内部 shift。附带发现：旧 GDN 权重在正确口径下 PPL ≈ 124k，完美解释了此前的"FLA eval-path per-token CE 异常"（那不是 FLA 的 bug，是我们自己的）。修正后 GDN@3k = 16.86（被削弱版 21.30，差 4.4 PPL）。

### 剩余边界（如实）

2. FLA 库依赖仍在快速路径（自研 delta_chunk 已就绪为备选，速度 2-4×）
3. 验证尺度 488M tokens / 101M 参数；更大规模需扩展算力

## 15. v47–v54：宽键封锁、肥层重构与三消融链（2026-11-10 ~ 11-13）

**解剖学定位（诚实）**：delta-rule 家族的写入方向/强度/内容**已全部逐 token 动态**——E1 的静态 A 在 dme 里不存在；GDN 同样动态，差距不在动态性。E1 对 dme 的真实增量 = **e_t 步身份轴**：递推算子（β/g）当前只受内容条件（v53g 内容调制衰减已失败 ❌），**位置条件从未测过**。

### ✅ O(1) 解码线程化（2026-11-26）：侧记忆接入逐 token 解码——旗舰此前**不能正确流式解码**，现已修复并验证

**问题（自 DMDA 线开始即标注"线程化未做"的欠账）**：侧记忆只存在于 prefill/评测路径（`chunk_*_delta_rule(..., initial_state=None, output_final_state=False)`），解码分支（sx==1）只更新主 KV 状态——**逐 token 解码时侧记忆被整个丢弃**。全部已归档评测用全序列前向（每窗 O(n)），数字有效；但模型作为 O(1) 流式解码器是坏的。

**同口径改动前后对照**（autocast bf16，T=512，prefill 256 + 逐 token 解码 256 步；旧代码 = 提交 `77b414b` 的 open_ash_v3）：

| 模型 | 版本 | logits \|Δ\| mean / max | argmax 一致率 | ppl 全序列 vs 解码 |
|---|---|---|---|---|
| dms@80k | 改动前 | 2.46 / 19.8 | **51.2%** | 11.523 vs **46.47** |
| dms@80k | **改动后** | 0.046 / 0.56 | **99.6%** | 11.523 vs **11.517** |
| dme@80k | 改动前 | 2.17 / 17.5 | 52.7% | 11.841 vs 45.05 |
| dme@80k | 改动后 | 0.041 / 0.34 | 99.2% | 11.841 vs 11.827 |
| dmh@80k | 改动前 | 2.50 / 19.6 | 50.4% | 11.218 vs 53.90 |
| dmh@80k | 改动后 | 0.040 / 1.66 | 99.2% | 11.218 vs 11.130 |

第二个窗口（起点 40000）结论一致：45–50% → 98.8–99.2%，ppl 6.6 vs 31 → 6.64 vs 6.64。

**实现**：侧记忆状态打包进层状态的 kv 槽位 `(s_kv, s_dm)`；prefill 接 `initial_state / output_final_state`；解码分支加 O(1) 单步——锚定 FLA 语义：`S ← a·S；corr = v − k·(a·S)；S ← a·S + (β·k)⊗corr；o = q·S·K^−0.5`（q/k/v/β/g 先按 prefill 同口径取 bf16，递推 fp32）。

**验证（四层）**：
1. **kernel 级语义（T1，带鉴别性反例）**：门控情形本实现 mean|Δo|/scale = 2.3e-3，"衰减前读"反例 2.0e-2（9×），"漏 K^−0.5"反例 6.5（2800×）；终态偏差 ≤0.5%
2. **prefill 不变性（T3'）**：改动前代码 vs 改动后代码，dms/dme/dmh/kr 四模型全序列前向 logits **逐位相同（|Δ|=0）**——所有已归档评测数字不受影响（注：我最初设计的 T3"全序列前 P 位 vs 单独 prefill"对未改动的 kr 也差 0.56，受其他组件在不同 T 下的数值差异污染，已作废替换）
3. **解码一致性（T2）**：见上表；fp32 模式下 dms 残差 mean 8.7e-3（无侧记忆的 kr 为 3.0e-3）——残差来源是侧记忆 prefill 走 bf16 kernel（当初为速度的选择），kernel 内部中间量有 bf16 舍入
4. **O(1) 证据（T4b，batch 1，eager + autocast）**：逐 token 解码延迟 **46.0 / 47.6 / 48.0 ms/token @ ctx 128/1024/2048**（恒定），携带状态 **14.01 MB**（恒定，7 层 × 2.0MB；侧记忆仅占 ~1MB）；对照 kr（无侧记忆，6 层）34.6–34.8 ms/token、12.65MB

**如实标注**：
- 绝对速度 21–22 tok/s 是 **Python/kernel 启动开销主导**的 eager 数字，非架构属性：T=2048 的全序列前向总共只要 51 ms（摊薄 0.025 ms/token），说明单 token 的 GPU 计算量远小于 1 ms；dms 比 kr 慢 ~35% 来自多 1 层 + 侧记忆每层十余个小算子的启动开销。CUDA Graph / 融合解码 kernel 可大幅改善，未做
- 早期报告的"45 tok/s 恒定"是 ASH-F1 的实测值；本次同规模 6 层的 kr 在 eager 口径下为 29 tok/s——两者的测量脚本不同，差异来源未核查，不可直接比较
- 一致性处于 bf16 噪声水平（argmax 98.8–99.6%），不是逐位等价

**结论**：架构自始至终是 O(1) 设计；**实现在本节之前不完整**（解码丢侧记忆），现在旗舰可在恒定状态、恒定逐 token 延迟下正确流式解码。
